## 2. 수정 요청 — 1건

**`uv_reapply` 푸시 본문**: *"설정하신 시간이 지났어요. 자외선 차단제를 다시 바를 타이밍이에요."*

- "다시 바를 타이밍이에요"는 같은 행동을 가리키는 `templates.py`의 "선크림 재도포 **확인**"이나 PRD §12.7 예시 문구("재도포 **확인**해 보세요")보다 **행동을 직접 지시하는 어감**입니다.
- PRD §14.7: "SPF, 피부 타입, 제품 성능에 따른 재도포 주기를 서비스가 판단하지 않는다" — 서비스는 사용자가 정한 주기가 됐다는 사실만 알리는 역할이지, "발라야 할 타이밍"이라고 재도포 필요성 자체를 판단하는 주체가 되면 안 됩니다.
- **수정 제안**: `"설정하신 시간이 지났어요. 자외선 차단제를 다시 확인해 보세요."` (PRD 예시·templates.py 톤과 통일)
- 담당: `WellnessActionCatalog.java` (김민형) — 한 줄 상수 수정, 골든 테스트 영향 없음(문자열 assert 하는 테스트 있으면 함께 수정 필요)

나머지 카피는 전부 "확인/준비/보충" 등 관찰·안내형 동사만 사용해 의료·효능 판단으로 읽히지 않습니다.

## 3. 금지 표현 체크 (PRD §14.8 · TR-09)

`templates.py` 상단 주석에 이미 명문화되어 있음 — **이 표를 코드 주석과 동일하게 유지하는 것을 승인 조건으로 확정**합니다.

| 금지 | 확인 |
|---|---|
| 진단·치료 표현 | 없음 ✅ |
| 복용량·용법 표현 | 없음 (영양제·복용약은 준비 항목으로만 취급, 웰니스 카피 대상 아님) ✅ |
| 피부 상태 판정 | 없음 ✅ |
| 제품 효능 보장 | 없음 ✅ |
| 건강 효과 확정 표현 | 없음 — 전부 "확인/보충/준비" 수준 ✅ (§2 수정 후 완전 충족) |

승인 목록 밖의 문자열이 알림·카드 렌더 경로에 들어가지 않는지는 TRD §17.5 카피 린트(CI)가 계속 검사 — 이 문서는 **그 통과 목록의 근거**로 사용한다.

## 4. A/B/C 실험 설계 (PRD §26.4)

이미 수집 중인 실제 필드(`Notification.deliveryStatus`, `WellnessEventSchedule.responseAction`, `DailyWellnessSummary`)를 기준으로 지표를 정의한다 — 새로 계측을 추가하지 않는다.

| 실험군 | 구성 | 측정 |
|---|---|---|
| A | 환경 수치만 표시 (카드에 UV/PM 숫자만) | 이해도, 준비 행동 완료율 |
| B | 환경 이유 + 외출 전 행동 제안 (현재 구현 상태) | 완료율, 유용성 |
| C | B + 선택형 일정 중 이벤트 푸시 (현재 구현 상태) | 재도포 반응률, 알림 해제율, 불필요 평가율 |

**현재 구현은 B+C가 이미 켜진 상태(§1)이므로, A는 별도 실험 없이 "카드에서 근거 문장만 숨긴 변형"으로 즉석 비교 가능.** 정식 A/B 인프라를 새로 만들 시간이 없으므로, 제출 데모에서는 A/B/C를 정량 비교하지 않고 **B+C 구성 그대로 제출**한다 — 실험은 베타 단계 과제로 넘김.

**지표 계산식 (실제 필드 기준)**

```
웰니스 행동 완료율   = responseAction='completed' 수 / 발송된 이벤트 스케줄 수
웰니스 알림 해제율   = responseAction='stop_today' 수 / 발송된 이벤트 스케줄 수
불필요 평가율        = (적합률 평가 API 연동 여부 확인 필요 — 없으면 이번 제출에서 제외)
전달 성공률          = deliveryStatus='delivered' 수 / deliveryStatus 전체 수
```

가드레일(적용은 베타 이후): 해제율 ≥30% 또는 불필요 평가율 ≥25% → 해당 actionCode의 WIS 임계 70→85 상향 (TRD D9, 이미 코드 반영 여부는 BE 확인).
