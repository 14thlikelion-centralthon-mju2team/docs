> 작성: 최수민 · M0 산출물 · 기준: PRD v0.4.3(최상위) · TRD v4.0 · API v5.0

## 1. P0 / P1 / P2 범위 (PRD §25 확정)

### P0 — 제출 빌드에 반드시 있어야 함
- 회원 로그인(이메일+Google), 필수 약관, 세션 유지, 로그아웃·탈퇴
- 내부·외부 캘린더 연동, 장소 필요 여부, 일정 분류
- 초기 준비 시간 시드 + 실패 기록 기반 자동 보정
- 준비 시작·출발·도착 시각 계산 + 계산 근거 표시
- 외부 지도 API 기반 기본 경로 검색 + 캘린더 저장
- 여유·극한·돌발 알림(일정당 최대 3회) + 알림 로그
- 환경 데이터 수집 + WIS 계산 + 외출 전 웰니스 행동 최대 3개
- 사용자 설정 기반 선크림 재도포 이벤트 푸시(일정당 기본 1회)
- 준비·출발·도착 결과 기록 + 원인 분리 보정
- 권한·개인정보·데이터 삭제 설정
- 준비시간 초기 화면의 나만의 준비 항목 빠른 설정 + 일정별 체크리스트 반영

### P1 — 시간이 되면, 안 되면 잘라도 되는 것
- 일정 유형·시간대별 준비 모델(MODEL-02)
- 개인 준비물·루틴의 조건 자동 적용
- 일일 마무리 카드(WELL-05) — **MILESTONE은 M4에 포함시켰음.** 데모에 필요하면 유지, 일정이 밀리면 가장 먼저 자를 것
- 주간 리포트(REPORT-03)
- 웰니스 알림 빈도 자동 개인화, 대체 이동 수단 제안

### P2 / 명시적 비목표 — 만들지 않는다
- 지도 환경 레이어, 센서 방향, 보행속도 추정, AR, 턴바이턴, 자체 지도 엔진
- 친구 위치 공유, 웨어러블 연동, 건강·피부 진단, 복약·치료 조언
- 웰니스 카피 자유 생성 LLM (승인 템플릿 외 문장 금지)
- 하루 전체 이동 경로 저장, 외부 캘린더 제목 원문 장기 보관

## 2. 화면별 핵심 인수 조건

전체 화면 설계는 `03_화면설계서.md`(설계 문서 세트) 참조. 아래는 **완료/미완료를 가르는 최소 기준**만 못박는다.

| 화면 | 완료 조건 (이것 없으면 미완료) |
|---|---|
| 로그인 | 이메일/Google 각각 성공·실패·재시도 3경로 모두 동작. 미인증 상태로 핵심 API 접근 시 차단 |
| 준비시간+맞춤항목 (온보딩) | "잘 모르겠어요" 선택 가능, 건너뛰기로 온보딩 완료 가능, 등록 항목이 다음 일정 체크리스트에 실제로 반영됨 |
| 홈 | 준비 시작/권장 출발/도착 예상 시각 + **계산 근거(펼침)** 동시 노출. 맞춤 항목 ≤3(+더보기), 웰니스 행동 ≤3. 환경 데이터 없을 때 웰니스 영역만 조용히 생략(시간 계획은 정상) |
| 지도 | 경로 후보 3종(빠른/도보적음/환승적음) 비교 후 [캘린더에 추가]로 프리필 일정 생성까지 끊김 없이 연결 |
| 캘린더 | 장소 필요/불필요/미지정 3상태 지정 가능, 사용자 지정값이 자동 분류를 항상 이김 |
| 일정 상세 | breakdown(개인준비·환경가산·루틴·이동·버퍼) + reasons 문장 + 체크리스트 + 결과(정시/촉박/지각) 모두 한 화면에서 확인 |
| 알림 로그 | 유형·발송시각·발생이유·반응·변경계획 표시. 일정당 시간 알림 3회·웰니스 1회 초과 시 이 문서 위반으로 간주 |
| 설정 | 개인화 초기화(행동기록 유지) / 탈퇴(전체 삭제, 동의이력만 보존) 구분 동작 |

## 3. 용어·enum 동결

문서마다 표기가 갈렸던 것을 여기서 하나로 고정한다. **이후 모든 문서·코드·PR은 이 표를 따른다.**

| 용어 | 확정 값 | 비고 |
|---|---|---|
| 인증 수단 | `email`, `google` 2종 | 이미 구현 진행 중(BE `feat/be-auth-platform`, FE `feat/fe-auth-onboarding`) — PRD는 소셜 로그인만 명시했으나 **이대로 확정**. PRD 문서는 사후 업데이트 예정 |
| 웰니스 이벤트 게이트 | **6개**: ①opt-in ②WIS≥70 ③야외노출지속 ④재알림간격도달 ⑤동일행동 미완료 ⑥항목별 일일상한 미소진 | PRD 5개 + TRD/API가 추가한 일일상한(⑥)을 채택. "4중 게이트"라는 TRD 소제목은 오기이므로 무시 |
| 웰니스 점수 | WIS(일정별 우선순위) · RLS(촉박함) · DWL(일일 부담) — **셋 다 건강 점수 아님, 알림 우선순위 값** | 화면·카피 어디에도 "건강 점수"로 표현 금지 |
| 보정 상한 | 1회 변화 **15분** (PRD §16.2 명문) | TRD 콜드스타트 예외 20분은 **채택하지 않음** — 15분으로 통일. 필요시 원격 설정값 조정은 베타 이후 |
| 리비전 상태 | `planStatus`(active/superseded) ≠ `eventStatus`(planned→…→closed) — 서로 다른 축 | 혼용 금지 |
| 일정 표시명 | `displayLabel`(사용자 입력·승인) → 없으면 목적지명 → 없으면 "오후 2시 일정" | 외부 캘린더 제목 원문은 미보관·즉시 폐기(분류 용도로만 사용). **이 정책으로 인해 외부 연동 일정의 실제 제목이 홈에 안 뜨는 것은 알려진 제약**(§5 참조), 버그 아님 |

## 4. 알림 예산 (고정값)

- 시간 관리 알림(여유A·극한B·돌발C): 일정당 **최대 3회**, 돌발은 최신 1건만 유지(교체)
- 웰니스 이벤트: 사용자 동의 시 일정당 **기본 1회** + 항목별 일일 상한(기본 1)
- 실질 변화 판정: Δ<2분 무시 / 2~5분 로그만 / Δ≥5분 또는 즉시예외(계획불가 전환·수단변경·강수급변) 시 푸시
- 준비/출발/완료 상태 입력 시 남은 예약 알림 전체 취소

이 표를 벗어나는 알림 로직 변경은 `docs/notification-policy` PR로만 반영한다.

## 5. 알려진 제약 (버그 아님, UAT에서 재현 시 이 문서를 먼저 확인할 것)

1. **외부 캘린더 일정의 실제 제목이 홈에 표시되지 않을 수 있음** — 제목 원문 미보관 정책 때문. 사용자가 `displayLabel`을 직접 입력하지 않으면 목적지명 또는 시간으로 대체 표시된다.
2. **도착(arrived) 처리와 행동기록 삭제 API의 최종 형태는 BE 쪽에서 확인 필요** — 이 계약서 범위 밖(기술 문서 쪽 이슈), UAT 설계 시 BE 담당자에게 현재 구현 상태를 먼저 확인할 것.
3. **일일 마무리 카드(P1)가 M4 일정에 포함되어 있음** — 시간이 부족하면 가장 먼저 잘라도 계약 위반이 아니다(§1 P1 참조).
